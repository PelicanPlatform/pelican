# Using a Transfer Server

A *transfer server* runs transfers on your behalf.
Instead of your client moving the data — or, for a [third-party copy](./third-party-copy), supervising the origins that move it — you hand the job to a server, which returns a job ID and carries the transfer out whether or not your client is still running.
That is the reason to use one: the transfer outlives your session, so you can submit a multi-hour copy, close your laptop, and let it finish.

<Callout type="info">
This page is about `--transfer-server`, which submits to a *remote* server.
It is a different mechanism from `--async`, which runs a transfer in the background on your own machine through the local client agent and is managed with `pelican job`.
</Callout>

## Submitting a transfer

Point `pelican object copy` at the server with `--transfer-server`:

```bash copy
pelican object copy --transfer-server https://transfer.example.com:8447 \
	pelican://<federation-url>/<namespace>/source \
	pelican://<federation-url>/<namespace>/destination
```

The command returns as soon as the server accepts the job:

```
Transfer job submitted: 0194f3c2-... (status: pending)
```

If the origin you are writing to runs its own embedded transfer service, you can name the origin instead and let the client discover it.
`--dest-origin` pings the origin first and fails fast if the service is not enabled there:

```bash copy
pelican object copy --dest-origin https://origin.example.com:8447 \
	pelican://<federation-url>/<namespace>/source \
	pelican://<federation-url>/<namespace>/destination
```

`--transfer-server` and `--dest-origin` are mutually exclusive.

### Waiting for the job

Add `--wait` to block until the job reaches a terminal state:

```bash copy
pelican object copy --transfer-server https://transfer.example.com:8447 --wait \
	pelican://.../source pelican://.../destination
```

While it waits, the client draws a progress bar for the job, the same way `object get` and `object put` do for transfers they run themselves.
The bar is drawn only when output is going to a terminal, and not at all if you have set `Logging.Client.DisableProgressBars` or directed logs to a file.

The command's exit status then reflects the job's outcome, which is what makes `--wait` the form to use in a script.

### Checking on a job later

Without `--wait` the command returns a job ID. `pelican transfer job` reports on jobs you submitted earlier:

```bash copy
pelican transfer job list --server https://transfer.example.com:8447
```

```bash copy
pelican transfer job status --server https://transfer.example.com:8447 <job_id>
```

`list` shows your own jobs, most recent first; `--status` narrows it to one state and `--limit`/`--offset` page through a long list.
Both commands report how much of the job has moved.
A job whose size is not yet known reports the bytes moved without a percentage, and one the server no longer holds in memory reports its progress as `unknown` — which is not the same as a job that has moved nothing yet.
`status` also takes `--wait`, which blocks until the job finishes just as `--wait` on the original command would — useful when you submitted a job, walked away, and now want to block on it.

To stop a job that is still running:

```bash copy
pelican transfer job cancel --server https://transfer.example.com:8447 <job_id>
```

Jobs that have already completed are unaffected by `cancel`.

<Callout type="info">
These commands report on jobs submitted to a transfer server.
Transfers you started locally with `--async` are a different thing and are managed with `pelican job`.
</Callout>

## Credentials

The server needs its own copy of a storage credential it can refresh while the job runs.
The first time you submit to a given server, the client arranges that for you:

1. It authenticates you to the transfer server. You are prompted to visit a URL and approve the request.
1. It obtains a storage credential for each end of the transfer and stores it on the server.
1. It remembers those credentials, so later transfers over the same namespaces reuse them without prompting.

In the common case this means you approve something in a browser once per server, and subsequent submissions are silent.

### Naming credentials explicitly

To pin a transfer to credentials you have already stored, give their IDs:

```bash copy
pelican object copy --transfer-server https://transfer.example.com:8447 \
	--source-credential-id <id> --dest-credential-id <id> \
	pelican://.../source pelican://.../destination
```

When both are supplied you are never prompted to approve anything.

### Managing stored credentials

`pelican transfer credential` lists, adds, and removes the credentials a server holds for you:

```bash copy
pelican transfer credential list --server https://transfer.example.com:8447
```

If you already hold a storage token, you can store it directly rather than going through OAuth:

```bash copy
pelican transfer credential add --server https://transfer.example.com:8447 \
	--name my-credential --issuer https://issuer.example.com \
	--access-token-file /path/to/token
```

The token is read from standard input if `--access-token-file` is omitted.
You can list a stored credential's name, issuer, and scopes, but the token itself is never returned.

Deleting one takes the credential's ID, which `list` reports:

```bash copy
pelican transfer credential delete --server https://transfer.example.com:8447 <id>
```

<Callout type="warning">
A credential you store is a token the server can use on your behalf until it expires or you delete it.
Store credentials only on a transfer server you trust, and delete them when you no longer need the access.
</Callout>

Servers clean up credentials that go unused; how long they are kept is up to the administrator.

### Supplying the API token yourself

`--transfer-server-token` takes a file containing a token for the transfer server's API, skipping the interactive approval step.
This is the flag to use from a batch job or any other context where no one can approve a browser prompt:

```bash copy
pelican object copy --transfer-server https://transfer.example.com:8447 \
	--transfer-server-token /path/to/api-token \
	--source-credential-id <id> --dest-credential-id <id> \
	pelican://.../source pelican://.../destination
```

This token authorizes *use of the API* only. It conveys no access to storage, so a non-interactive submission normally names its credential IDs as well.
